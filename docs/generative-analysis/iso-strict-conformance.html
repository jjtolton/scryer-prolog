ISO Prolog Strict Conformance

Understanding Strictly Conforming Mode and Scryer Prolog's Path Forward

Executive Summary

Key Finding: Scryer Prolog is currently a conforming processor that passes all syntactic conformity tests but is NOT strictly conforming due to its numerous extensions beyond the ISO standard. Adding a strictly conforming mode would require significant architectural changes but is technically achievable.

Quick Overview

  • Current Status: Conforming ISO Prolog processor with extensions
  • Syntactic Conformity: ✓ Passes all tests
  • Strict Conformance: ✗ Uses many non-ISO features
  • Primary Challenge: Architectural separation of ISO core from extensions

What Does "Strictly Conforming" Mean?

ISO/IEC 13211-1:1995 Definitions

The ISO Prolog standard (Section 5: Compliance) defines three levels of conformance:

Conformance Level Definition Use Case
Strictly Conforming Uses ONLY features defined in the ISO standard. No implementation-specific or implementation-defined extensions. Maximum portability across all ISO Prolog processors
Conforming May use implementation-defined and implementation-specific features, but all such features must be documented. Balance between portability and platform-specific capabilities
Conforming Processor Correctly executes strictly conforming Prolog text AND documents all extensions and deviations. Standard-compliant implementation that can also provide extensions

Critical Distinction

Strictly conforming TEXT is Prolog code that uses only ISO features.

Conforming PROCESSOR can execute strictly conforming text AND may offer extensions.

Scryer Prolog is a conforming processor, but most Scryer Prolog programs are NOT strictly conforming text.

What the Standard Says Exactly

"Conforming Prolog text is character sequences satisfying all compliance clauses for Prolog text, representing directives and clauses as read-term sequences. Conforming Prolog data consists of character and byte sequences satisfying all data compliance clauses. Both must adhere to syntax specifications, semantic constraints, and any declared implementation-specific extensions."
"Implementation-specific features are undefined by the standard but supported by conforming processors while preserving syntax/semantics of strictly conforming text."

Practical Implications

A strictly conforming mode in Scryer Prolog would mean:

  1. Rejected Features: All non-ISO predicates, directives, and syntax extensions would be flagged as errors
  2. Limited Built-ins: Only the ~100 built-in predicates specified in ISO/IEC 13211-1:1995
  3. No Extensions: No attributed variables, tabling, CLP, delimited continuations, etc.
  4. Strict Flags: All Prolog flags would be limited to ISO-defined values
  5. Error on Import: Attempting to load non-ISO libraries would fail
  6. Guaranteed Portability: Code running in strict mode would be guaranteed to run on ANY conforming ISO Prolog processor

How Scryer Prolog Deviates from Strict Conformance

1. Extended Built-in Libraries (46+ Non-ISO Modules)

Major Deviation: Scryer provides 46+ library modules, of which only a tiny fraction overlaps with ISO requirements.

2. Attributed Variables (SICStus-style)

One of Scryer's major features is support for attributed variables following the SICStus Prolog interface:

  • verify_attributes/3
  • attribute_goals/2
  • project_attributes/2
  • call_residue_vars/2

ISO Status: ❌ Attributed variables are NOT part of ISO/IEC 13211-1:1995

3. Partial String Representation

Scryer uses a packed internal representation for strings as difference lists of characters. This is an implementation optimization not specified in ISO.

ISO Status: ⚠️ Implementation-dependent (allowed as optimization, but affects observable behavior)

4. Extended Arithmetic & Number Types

  • Rational Numbers: Full rational arithmetic support
  • Arbitrary Precision: Bignum integers beyond max_integer

ISO Status: ⚠️ Partial conformance (ISO allows but doesn't require rationals; bignums are implementation-dependent)

5. Module System

Scryer implements a revised module system. While ISO/IEC 13211-2:2000 defines modules, the base standard (Part 1) does not.

ISO Status: ⚠️ ISO Part 2, not Part 1 (strict conformance is to Part 1 only)

6. Extended Directives

Scryer supports many directives beyond the ISO-mandated set:

  • :- use_module/1, :- use_module/2
  • :- module/2
  • Various implementation hooks

ISO Directives: Only :- dynamic/1, :- multifile/1, :- discontiguous/1, :- op/3, :- initialization/1

7. Global Variables (Backtrackable and Non-backtrackable)

bb_get/2, bb_put/2, bb_b_put/2

ISO Status: ❌ Not in ISO standard (common extension in many Prologs)

8. Extended I/O and Streams

While Scryer implements the ISO stream model, it extends it with:

  • Socket streams (TCP connections as streams)
  • HTTP streams
  • TLS-encrypted streams
  • Process pipe streams

ISO Status: ⚠️ Extensions on top of ISO stream model

What It Would Take to Add "Strictly Conforming Mode"

Architectural Requirements

Core Challenge

The primary challenge is not making Scryer execute ISO-conforming code (it already does this). The challenge is creating a mode that rejects all non-ISO features while maintaining the existing extended functionality.

Required Changes

Phase 1: ISO Core Isolation

  • Identify and catalog all 100+ ISO-mandated built-in predicates
  • Create ISO-only predicate whitelist
  • Separate ISO core from extended predicates in codebase
  • Tag all library modules as ISO/non-ISO
  • Create compile-time feature flag STRICT_ISO_MODE

Phase 2: Loader & Parser Modifications

  • Modify loader (src/machine/loader.rs) to check mode
  • Add strict mode validation in parser
  • Implement directive filtering (reject non-ISO directives)
  • Add runtime checks for predicate calls
  • Implement error reporting for non-ISO feature usage

Phase 3: Flag & Configuration System

  • Add Prolog flag iso_strict_conformance (on/off)
  • Command-line option: --strict-iso
  • Environment variable: SCRYER_ISO_STRICT=1
  • Runtime toggle: set_prolog_flag(iso_strict_conformance, on)

Phase 4: Library Isolation

  • Create src/lib/iso/ directory for ISO-only predicates
  • Move ISO predicates from extended libraries to ISO core
  • Implement library loading guards (reject non-ISO in strict mode)
  • Document which predicates from iso_ext.pl should be ISO core

Phase 5: Testing & Validation

  • Create comprehensive test suite for strict ISO mode
  • Verify rejection of all non-ISO features
  • Test compliance with ISO test suite
  • Ensure no regressions in normal (extended) mode
  • Performance benchmarking (strict vs. extended)

Phase 6: Documentation

  • Document all ISO vs. non-ISO predicates
  • Create migration guide for strict mode
  • Update README with strict conformance information
  • Add examples of strictly conforming programs

// In src/machine/loader.rs
impl Loader {

        if self.config.iso_strict_mode {
            if !is_iso_module(module_name) {
                return Err(LoadError::NonISOModule {
                    module: module_name.to_string(),
                    message: format!(
                        "Module '{}' is not part of ISO/IEC 13211-1:1995. \
                         Disable strict ISO mode to use extended features.",
                        module_name
                    )
                });
            }
        }
        // ... existing load logic
    }
}

// In src/machine/dispatch.rs
fn execute_goal(&mut self, goal: &Goal) -> ExecutionResult {
    if self.machine_state.flags.iso_strict_conformance {
        let (name, arity) = goal.predicate_indicator();
        if !is_iso_predicate(&name, arity) {
            return Err(MachineError::existence_error(
                "procedure",
                format!("{}/{}", name, arity),

        }
    }
    // ... existing execution logic
}

Recommendations

Recommended Approach: Phased Implementation

Phase 1: Implement static analysis tool (--check-iso-strict flag)

Phase 2: Add runtime strict mode with clear error messages

Phase 3 (Optional): Consider separate Scryer-ISO distribution if demand exists

Rationale

  1. Static Analysis First: Provides immediate value with minimal risk. Developers can check their code for ISO conformance without runtime overhead.
  2. Runtime Mode Second: After static analysis is proven useful, invest in runtime mode for guaranteed enforcement and teaching purposes.
  3. Separate Distribution Last: Only pursue if there's demonstrated demand for a pure ISO Prolog (e.g., academic use, certification requirements).

Conclusion

Scryer Prolog is currently an excellent conforming processor that extends the ISO standard with modern, powerful features. Adding a strictly conforming mode is technically feasible and would serve specific use cases (education, portability, certification), but requires significant architectural work.

Key Takeaways

  • Current Status: Conforming processor with extensive extensions (46+ libraries, attributed variables, tabling, CLP, etc.)
  • Syntactic Conformity: Already achieved (passes all tests)
  • Strict Conformance Gap: Architectural - needs separation of ISO core from extensions
  • Implementation Approach: Phased strategy starting with static analysis, followed by runtime mode
  • Value Proposition: Primarily benefits academic users, library developers, and those requiring vendor independence

Next Steps

  1. Community Discussion: Gauge interest in strict conformance mode among Scryer users
  2. ISO Audit: Comprehensive catalog of all predicates/features against ISO standard
  3. Prototype: Implement static analysis tool as proof-of-concept
  4. Evaluation: Assess usage and feedback before committing to full runtime mode

The decision to pursue strict conformance should be driven by demonstrated user need rather than theoretical completeness. Scryer's strength lies in its modern extensions while maintaining a solid ISO foundation.
